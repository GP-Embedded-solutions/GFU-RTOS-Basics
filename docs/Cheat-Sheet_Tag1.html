System prüfen — läuft ein RT-Kernel?

uname -aMuss PREEMPT_RT enthalten
cat /sys/kernel/realtimeMuss 1 sein (fehlt bei Standardkernel)
zcat /proc/config.gz | grep PREEMPTCONFIG_PREEMPT_RT=y suchen
ps -eLo pid,class,rtprio,comm | grep irq/IRQ-Handler als eigene Threads = RT
cat /proc/device-tree/modelHardware-Modell bestätigen
nprocAnzahl CPU-Kerne

Kernel umschalten (Kurs-Setup)

sudo ./switch-kernel.sh rtPREEMPT_RT aktivieren + Reboot
sudo ./switch-kernel.sh stdStandardkernel + Reboot
./switch-kernel.sh statusZustand anzeigen, kein Reboot
sudo ./switch-kernel.sh isolate onisolcpus=2,3 setzen (Tag 2)
Falle: Bei eigenem Kernel-Dateinamen setzt start4.elf arm_64bit nicht automatisch. Ohne arm_64bit=1 in config.txt bootet der Pi 4 nicht.

cyclictest — die wichtigsten Flags

-mmlockall: Speicher sperren, Page-Faults vermeiden
-SSMP-Modus: ein Thread pro CPU-Kern
-p 99SCHED_FIFO-Priorität (1–99)
-i 1000Intervall in Mikrosekunden
-D 60sLaufzeit (auch 1m, 2h)
-h 400Histogramm bis 400 µs ausgeben
-a 3Auf CPU-Kern 3 festnageln
-t 4Anzahl Threads explizit
-qLeise, nur Endergebnis

Standardaufruf für den Kurs

sudo cyclictest -m -S -p 99 -i 1000 -h 400 -D 60s
Ohne Last gemessen = wertlos. Immer parallel:
stress-ng --cpu 4 --io 4 --vm 2 --vm-bytes 128M -t 70s

Moderne Alternativen (rtla)

sudo rtla timerlat top -d 30sTimer-Latenz, aufgeschlüsselt nach IRQ und Thread
sudo rtla osnoise top -d 30sZeigt wohin die Zeit geht
sudo rtla timerlat hist -d 30sHistogramm-Ausgabe
Unterschied: cyclictest sagt dass es ruckelt. osnoise sagt warum.

Boot-Parameter · I²C · Scheduling · Code-Muster

Boot-Parameter — /boot/firmware/cmdline.txt

Eine einzige Zeile. Kein Zeilenumbruch. Wirksam nach Reboot.

isolcpus=2,3Kerne 2 und 3 vom Standard-Scheduler ausnehmen
nohz_full=2,3Scheduler-Tick auf diesen Kernen abschalten
rcu_nocbs=2,3RCU-Callbacks auf andere Kerne verlagern
irqaffinity=0,1Interrupts nur auf Kern 0 und 1
threadirqsIRQ-Handler als Threads (bei RT bereits Standard)
processor.max_cstate=1Tiefe Schlafzustände verhindern (x86)
Die drei gehören zusammen. isolcpus allein reicht nicht — Tick und RCU stören weiter.

Firmware — /boot/firmware/config.txt

arm_64bit=1Pflicht bei eigenem Kernel-Dateinamen
kernel=kernel8-rt.imgWelcher Kernel geladen wird
dtparam=i2c_arm=onI²C aktivieren
dtparam=i2c_arm_baudrate=400000Fast Mode, 400 kHz
force_turbo=0Kein dynamisches Übertakten

Scheduling

chrt -f 80 ./programmSCHED_FIFO Priorität 80 starten
chrt -p <pid>Policy eines Prozesses abfragen
chrt -f -p 80 <pid>Laufenden Prozess umstellen
taskset -c 3 ./programmAuf CPU 3 festnageln
ps -eLo pid,class,rtprio,ni,commAlle Threads mit Policy und Priorität

Prioritäten — Faustregel

99Reserviert — Finger weg
80–90Kritische Regelschleife
50–79Wichtige Echtzeitaufgaben
1–49Weiche Echtzeit
SCHED_OTHERAlles Nichtkritische
Warnung: SCHED_FIFO ist nicht präemptiv gegen gleiche Priorität. Eine Endlosschleife mit Priorität 99 friert das System ein. Immer mit -D oder Watchdog testen.

Das Code-Muster für zyklische Aufgaben

FALSCH — Fehler akkumuliert:
while(1) { arbeite(); usleep(100000); }
Periode = 100 ms + Arbeitszeit. Driftet.
RICHTIG — absolute Deadline:
clock_gettime(CLOCK_MONOTONIC, &next);
while(1) {
  ts_add_ns(&next, PERIODE_NS);
  clock_nanosleep(CLOCK_MONOTONIC,
    TIMER_ABSTIME, &next, NULL);
  arbeite();
}
CLOCK_MONOTONICSpringt nie. Immer diese Uhr.
CLOCK_REALTIMEKann durch NTP springen — auch rückwärts
TIMER_ABSTIMESchläft bis Zeitpunkt, nicht für Dauer
mlockall(MCL_CURRENT|MCL_FUTURE)Page-Faults verhindern
tv_nsec normalisieren! Über 999.999.999 gibt clock_nanosleep EINVAL zurück.
