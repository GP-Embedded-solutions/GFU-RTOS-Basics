Analyse-Werkzeuge — Schnellreferenz

ftrace / trace-cmd

sudo trace-cmd record -e sched:sched_switch \
     -e sched:sched_wakeup -e irq:irq_handler_entry \
     -e irq:irq_handler_exit -o trace.dat sleep 5
sudo trace-cmd report -t trace.dat | less

perf

sudo perf stat -e context-switches,cpu-migrations \
     ./programm
sudo perf record -g ./programm; perf report
sudo perf top -C 3   # nur auf Kern 3

rtla (osnoise / timerlat) — der verifizierte Fallback

sudo rtla osnoise top -d 30s -P f:99 -c 3
sudo rtla timerlat top -d 30s -P f:99 -c 3
sudo rtla timerlat hist -d 30s -P f:99 -c 3

Telemetrie & Architektur der Entkopplung

Stufe 3 — stage3_telemetry Aufrufe

Referenz ohne Telemetrie

sudo ./stage3_telemetry --fifo 80 --mlock --cpu 3 \
     --period 10 --duration 120 --csv lauf_A.csv --quiet

Richtig — entkoppelt via Ringpuffer

sudo ./stage3_telemetry --fifo 80 --mlock --cpu 3 \
     --period 10 --duration 120 \
     --influx <notebook-ip>:8086 --org kurs \
     --bucket echtzeit --token kurs-token-2026 \
     --tag-lauf stufe3_entkoppelt \
     --csv lauf_B.csv --quiet

Absichtlich falsch — zum Vergleich

sudo ./stage3_telemetry --fifo 80 --mlock --cpu 3 \
     --period 10 --duration 120 --demo-blocking \
     --influx <notebook-ip>:8086 --org kurs \
     --bucket echtzeit --token kurs-token-2026 \
     --tag-lauf stufe3_blockierend \
     --csv lauf_C.csv --quiet

Die eine Regel der Architektur

Der RT-Thread ruft niemals etwas auf, das blockieren kann.

RT-ThreadSCHED_FIFO, isolierter Kern, schreibt nur in Ringpuffer
RingpufferLock-frei (SPSC, C11-Atomics), kein Mutex, kein malloc
Voll?Älteste Messung wird verworfen — nie blockieren
Sender-ThreadSCHED_OTHER, andere Kerne, darf warten/scheitern
